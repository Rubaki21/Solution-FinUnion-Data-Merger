## Ключевые различия

| понятие                   | значение                                                    | пример                                                |
| ------------------------- | ----------------------------------------------------------- | ----------------------------------------------------- |
| System of Entry           | система, в которой факт впервые вводится или возникает      | заявка клиента появляется в канале/CRM                |
| Source System             | система, из которой физически извлекается копия данных      | Party может извлекаться из CRM, Core и Loans          |
| System of Record / Master | авторитетная система для определённой сущности или атрибута | остаток - Core Ledger, статус карты - Card Processing |
| MDM / Customer Hub        | разрешает идентичность, хранит golden record и crosswalk    | глобальный Party ID и подтверждённые контакты         |
| Consumer / Projection     | получает копию для своего сценария и не становится мастером | DWH, BI, поисковый индекс                             |

Одна система может совмещать несколько ролей, но они фиксируются отдельно. Наличие записи в DWH или MDM само по себе не делает компонент мастером

## Архитектурные решения

1. На горизонте трёх месяцев существующие FU/RB OLTP остаются мастерами открытых в них договоров, счетов, карт, кредитов, платежей, проводок и остатков
2. MDM Customer Hub становится мастером глобальной идентичности Party, crosswalk и золотых клиентских атрибутов, но не финансовых фактов
3. Для продукта и справочников сначала вводится канонический mapping; целевым мастером становится Product Catalog / Reference MDM
4. Integration Layer централизует доставку, валидацию, маршрутизацию и наблюдаемость. Он не владеет бизнес-данными
5. DWH принимает инкременты и снимки, выполняет историзацию, агрегацию и сверку. BI и регуляторная отчётность не читают OLTP напрямую
6. Все потоки используют глобальный Party ID вместе с исходным ключом и `source_system`, чтобы сохранить lineage
7. Обратная синхронизация разрешена только для явно назначенных мастер-атрибутов. Произвольный bi-directional update запрещён
8. BIAN задаёт семантические границы владения: Party, Agreement, Account, Card, Loan, Payment, Financial Accounting и Customer Case не смешиваются в одного владельца

## Объём промежуточного состояния

Через три месяца должны работать:
- минимальный MDM Customer Hub с match/merge, crosswalk и очередью Data Steward
- адаптеры FU/RB к Integration Layer
- CDC либо надёжные инкрементальные выгрузки критичных сущностей
- доставка глобального Party ID обратно в CRM и аналитический контур
- консолидированный DWH с витринами Party, договоров/продуктов, счетов/остатков и операций
- единый BI semantic layer
- каталог/DataHub с владельцами, классификацией, схемами и техническим lineage
- source-to-target и финансовые сверки, DLQ, мониторинг свежести и полноты
- регуляторная выгрузка только из сертифицированной зоны DWH после контроля

Не входят в трёхмесячный этап: массовый перенос финансовых мастеров, прямое отключение RB Core/Cards/Loans, единая физическая БД и синхронная зависимость клиентских операций от DWH или каталога

## Сквозные правила

- Для каждого потока определены ID, владелец, схема, SLA, DQ-контроли и runbook
- Каждое сообщение содержит `event_id`, `event_type`, `schema_version`, `source_system`, исходный ключ, `occurred_at`, `produced_at`, correlation ID и классификацию данных
- Потребители идемпотентны; порядок гарантируется в пределах бизнес-ключа, а не глобально
- Некорректные записи попадают в карантин/DLQ и учитываются в сверке, а не отбрасываются
- Проведённые финансовые факты исправляются сторно/корректировкой, а не удалением или перезаписью
- Delete означает логическое закрытие или контролируемое удаление по retention; для финансовых данных физический Delete через интеграционный поток запрещён
