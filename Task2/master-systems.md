
## Правила выбора

1. Мастер назначается не `на таблицу`, а на `бизнес-сущность` или `группу` атрибутов
2. Система первичного ввода не обязательно является мастером: канал может принять команду, но мастер подтверждает факт и назначает итоговый статус
3. В переходный период мастер финансовой сущности определяется атрибутом `servicing_system`: FU и RB работают параллельно, но одна конкретная запись имеет только один активный мастер
4. MDM управляет идентичностью, golden attributes и crosswalk. Он не вычисляет остатки, не проводит платежи и не меняет договорные условия
5. DWH, BI, DataHub/каталог, Integration Layer, Lakehouse и поисковые индексы - потребители/проекции, а не мастера операционных сущностей
6. Внешний нормативный классификатор может быть authority; Reference MDM тогда является внутренним мастером распространения его проверенной версии

## Мастерство на уровне атрибутов

Для нескольких сущностей одного мастера на все атрибуты недостаточно

| Сущность | Атрибуты | Мастер |
|---|---|---|
| Party | глобальный ID, crosswalk, golden name, подтверждённые контакты | MDM Customer Hub |
| Party | локальный operational ID и технический статус записи | соответствующая CRM/OLTP |
| Party | KYC-статус и дата проверки | KYC/AML-компонент; MDM публикует согласованную проекцию |
| Договор | draft/намерение | CRM или канал |
| Договор | юридический статус, стороны, подписанные условия | Core/Cards/Loans по типу договора |
| Карта | статус выпуска, блокировки, PAN token, срок | Card Processing |
| Карта | маркетинговое наименование и сегмент | Product Catalog/MDM |
| Кредит | договор, график, задолженность, просрочка | Loan System |
| Кредит | утверждённая риск-классификация | Risk domain; Loan System потребляет результат |
| Остаток | online available balance | обслуживающая Core/Card/Loan OLTP |
| Остаток | официальный EOD balance | Core Ledger; DWH хранит сертифицированную историческую копию |
| Продукт | экономическая конструкция и утверждение | Product Design |
| Продукт | опубликованная версия, коды и период доступности | Product Catalog |

## Матрица распространения

| Мастер | Что публикует | Основные потребители | Разрешённая обратная запись |
|---|---|---|---|
| MDM Customer Hub | `global_party_id`, crosswalk, golden attributes, merge/split events | CRM, Core, Cards, Loans, DWH, BI | CRM/KYC присылают кандидаты изменений; прямое изменение golden record запрещено |
| Product/Reference Hub | глобальные коды, версии, mapping FU/RB | Integration Layer, DWH, BI, доменные OLTP | Только через workflow владельца справочника |
| Core Banking / Ledger | счета, платежи, проводки, остатки, core-договоры | CRM/profile, DWH, regulator via DWH | Команды только через бизнес-API; аналитические системы не пишут |
| Card Processing | карты, карточные статусы и операции | CRM/profile, Core, DWH | Блокировка/перевыпуск через авторизованную команду, не через data sync |
| Loan System | кредиты, графики, задолженность, кредитные события | CRM/profile, Core, DWH, Risk | Изменения через кредитный процесс и maker-checker |
| CRM / Case Management | обращения, SLA, результат; данные первичного контакта | Customer Hub, DWH, BI | MDM возвращает только разрешённые golden attributes и global ID |
| ECM | оригинал документа, версия, hash, retention state | Связанная OLTP, аудит, уполномоченные пользователи | Новая версия/статус; подписанный оригинал не перезаписывается |

## Как BIAN ограничивает владение ?

- `Party Data Management` владеет идентичностью стороны, но не её счетами и остатками
- `Customer Agreement` владеет юридическими отношениями, но не определением продукта и не проводками
- `Current/Savings Account` владеет жизненным циклом счёта; `Financial Accounting` - бухгалтерским отражением
- `Issued Device Administration` владеет картой; `Card Authorization/Transaction` - событиями её использования
- `Consumer/Corporate Loan` владеют кредитным экземпляром и графиком, а Risk domain - независимо рассчитанной оценкой риска
- `Payment Order/Execution` владеют распоряжением и исполнением, `Financial Accounting` - результатом в книге
- `Customer Case Management` владеет обращением и SLA, читая Party/Agreement/Transaction по ссылке

Такое разделение предотвращает появление `супер-MDM`, двусторонние циклы обновлений и конкурирующие мастер-записи

## Правило разрешения конфликтов

1. Определить сущность, атрибут, `servicing_system` и business time конфликтующих версий
2. Применить утверждённую матрицу attribute ownership; `последняя запись победила` не является общим правилом
3. Для Party использовать survivorship и confidence; неоднозначность направлять Data Steward
4. Для договорных и финансовых данных принимать только версию профильного мастера и инициировать сверку
5. Сохранить обе исходные версии, решение, автора, время и причину; исправление публиковать новым событием
